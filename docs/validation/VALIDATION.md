# Slipstream Engineering Validation Report

**Status: template — no benchmark run has been recorded yet.**
This document defines the validation process and the exact fields a
completed run must report. It intentionally contains no fabricated
numbers; every data-dependent field below is marked `PENDING` until a
real benchmark has been executed and its results dropped into
`docs/validation/benchmark/`.

---

## 1. Purpose

To demonstrate, with reproducible evidence rather than assertion, that
Slipstream's automated Workbench + Fluent pipeline produces aerodynamic
results consistent with a trusted, independent reference — and to give
every future release a repeatable process for re-checking that claim
after an engine, ANSYS version, or dependency change.

This report is an engineering record, not marketing copy: every claim
here must be traceable to a specific reference source, a specific config,
and a specific run.

## 2. Validation philosophy

- **Comparison, not certification.** This process checks agreement
  against a reference dataset within a stated tolerance; it does not
  certify Slipstream (or ANSYS Fluent) for any regulatory or safety
  purpose.
- **Reproducibility over a single good result.** A validation run is only
  meaningful if a different engineer, on a different machine, with the
  same config and reference dataset, gets the same comparison metrics
  (within solver/mesh-dependent noise, which itself must be documented,
  not hidden).
- **The reference is external.** Reference data must come from a source
  independent of this codebase (published wind-tunnel data, an
  established CFD benchmark case, or a separately-validated solver run)
  — never numbers generated by Slipstream itself.
- **Tools separate from claims.** The comparison utilities
  (`tools/validation/`) compute metrics mechanically and deterministically
  from whatever two CSVs they're given; the pass/fail judgment against an
  acceptance tolerance (§9) is made by an engineer reading the output, not
  automated into a boolean.

## 10. Acceptance criteria

Default tolerance (adjust and record per run — see
`tools/validation/README.md` for how these map to the comparison
tool's output):

| Metric | Suggested tolerance |
|---|---|
| CL | MAE ≤ 0.02, max abs error ≤ 0.05 |
| CD | MAE ≤ 0.002, max abs error ≤ 0.005 |
| L/D | MAE ≤ 5% of reference L/D |

These are starting points, not physics — a real benchmark case should
justify its own tolerance from known mesh/turbulence-model sensitivity,
not just copy the table above.

## 11. Limitations

- No benchmark run has been recorded in this repository yet (see status
  banner above) — this document is process + schema, not evidence.
- The comparison tooling (`tools/validation/`) checks numerical agreement
  only; it cannot detect a reference dataset that is itself wrong, or a
  config error that happens to move both datasets the same way.
- RANS turbulence models (Slipstream's current solver path) are known to
  under-predict CD and mis-predict stall onset — any comparison near or
  past stall AOA should be treated as informational, not a validation
  failure, unless the reference itself used the same turbulence model.
- This process validates *aerodynamic coefficients*, not mesh convergence
  (a separate mesh-independence study — tracked as a future item in
  [`docs/PRODUCT_BACKLOG.md`](../PRODUCT_BACKLOG.md) — would be needed to
  separate solver-model error from mesh-resolution error).

## Workflow to complete this report

1. Run the real study in Slipstream against the reference geometry/BCs (§5–8).
2. Export results: `python main.py export-study <name> --out docs/validation/benchmark/slipstream/<name>.csv`.
3. Drop the reference dataset CSV into `docs/validation/benchmark/reference/`.
4. `python -m tools.validation.compare docs/validation/benchmark/reference/<ref>.csv docs/validation/benchmark/slipstream/<name>.csv --out-dir docs/validation/benchmark --plots`
5. Review `comparison_summary.json`/`comparison_table.csv` against §10's
   acceptance criteria, and the generated plots in
   `docs/validation/benchmark/plots/`.
6. Replace every `PENDING` field above with the real values, remove the
   status banner, and update
   [`docs/RELEASE_CHECKLIST.md`](../RELEASE_CHECKLIST.md)'s validation
   items for the release this run supports.
